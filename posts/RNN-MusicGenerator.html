Language models

Training an RNN to write Irish folk music

A character-level LSTM made sequence memory, sampling, and tensor shapes much more concrete than a diagram could.

31 July 20268 min readLearning source: MIT Introduction to Deep Learning, Lab 1

Why music is a useful sequence problem

Irish folk tunes written in ABC notation are plain text: notes, bar markers, durations, and headers are all characters. That means the task can be framed like a tiny language model—given the characters so far, predict the next one. The result can also be rendered as music, making structural mistakes easy to hear.

What the recurrent state does

A feed-forward model treats examples independently. A recurrent network carries a hidden state from one time step to the next, so the current prediction depends on both the new character and a learned summary of earlier characters.

A basic RNN can struggle to preserve useful information across long spans because gradients repeatedly pass through the same transformation. An LSTM adds a cell state and learned input, forget, and output gates. Those gates create a more controlled path for memory and gradients.

The model

class LSTMModel(nn.Module):
    def __init__(self, vocab_size, embedding_dim, hidden_size):
        super().__init__()
        self.embedding = nn.Embedding(vocab_size, embedding_dim)
        self.lstm = nn.LSTM(embedding_dim, hidden_size, batch_first=True)
        self.output = nn.Linear(hidden_size, vocab_size)

    def forward(self, tokens, state=None):
        x = self.embedding(tokens)
        x, state = self.lstm(x, state)
        return self.output(x), state

The embedding maps integer character IDs to dense vectors. The LSTM transforms a sequence of those vectors while updating hidden and cell state. The linear layer converts every LSTM output into vocabulary logits.

Training and generation are different

During training, the target is the same sequence shifted by one position. Cross-entropy compares every predicted distribution with the true next character. During generation, I seed the model, sample one predicted character, append it, and feed that character back in with the updated state.

pᵢ = softmax(logitsᵢ / temperature)

Temperature controls randomness. A low value sharpens the distribution and makes generation safer but repetitive. A higher value spreads probability across more characters, adding variety and also more errors. Sampling is therefore part of model behavior, not an afterthought.

The CUDA error that was really a shape error

Generation initially failed with a device-side assertion. CUDA reports work asynchronously, so the traceback did not point clearly to the original mistake. Running the same small path on CPU exposed it: after torch.multinomial, the sampled index had lost the batch dimension.

next_id = torch.multinomial(probs, num_samples=1)
next_input = next_id.view(1, 1)  # [batch, sequence]

The state still represented a batch of one, while the next token no longer had the expected two-dimensional input shape. Restoring [1, 1] fixed the loop.

What stayed with meSequence models are mostly about state and shape discipline. Understanding what every axis represents made both the architecture and the debugging much easier.
