Mtrace: watching a process talk to the kernel

A process tracer turned syscalls, registers, address spaces, and signals from textbook definitions into observable events.

10 August 20268 min readOperating Systems project

The boundary I wanted to see

User programs cannot directly open files, allocate protected memory, or talk to devices. They request those services through system calls. Mtrace observes that boundary by letting one process—the tracer—control another—the tracee.

The tracing loop

The tracee requests tracing before replacing itself with the target program. The parent waits for each stop, resumes execution until the next syscall boundary, then inspects the tracee’s registers.

// child
ptrace(PTRACE_TRACEME, 0, NULL, NULL);
execvp(argv[1], &argv[1]);

// parent
while (waitpid(child, &status, 0) > 0) {
    if (WIFEXITED(status)) break;
    ptrace(PTRACE_GETREGS, child, NULL, ®s);
    log_syscall(regs.orig_rax, regs);
    ptrace(PTRACE_SYSCALL, child, NULL, NULL);
}

On x86-64 Linux, the syscall number and arguments live in defined registers. A syscall normally generates two stops—one on entry and one on exit. Tracking that state lets the tracer show arguments on entry and the return value on exit without printing a confusing duplicate.

Reading another address space

A register may contain a pointer to a filename, but that address belongs to the tracee. Dereferencing it in the tracer reads the wrong virtual address space. I reconstructed strings a machine word at a time with PTRACE_PEEKDATA, stopping at the null terminator and handling failed reads.

Signals are part of correctness

Not every stop is a syscall stop. The tracee may receive SIGINT, SIGSEGV, or another signal. The tracer must inspect the wait status and decide whether to deliver the signal when resuming the child. Swallowing it changes program behavior; forwarding the wrong one can terminate the tracee unexpectedly.

Tracing should be transparentAn observation tool is only trustworthy when the observed process behaves as closely as possible to an untraced process. Signal forwarding is therefore not just an extra feature.

Making the output usable

A correct tracer can still be hard to use if it prints an endless stream. I added filtering, file logging, and an ncurses interface that keeps the current trace visible in a bounded terminal view. The interface did not change the tracing algorithm, but it changed whether I could reason about the output.

Why this connects to ML systems

Model performance depends on more than matrix multiplication. Data loading, memory mapping, filesystem access, process creation, and device communication all cross system boundaries. Learning to observe those boundaries is one step toward understanding why a workload is slow, blocked, or using resources unexpectedly.
